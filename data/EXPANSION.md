# Dev set → 400-item eval set: expansion plan

The 20-item dev set has done its job as a smoke test and is now measurably exhausted: [`ITEM-AUDIT.md`](ITEM-AUDIT.md) (generated by `scripts/itemcheck.py` from the committed reports) says **7 of 20 items are saturated** — every run scored them 1.00, including a small model with no doctrine prompt. Those seven items cost GPU-hours and measure nothing.

The 400-item set is the fix. This page is the plan, with the target numbers stated before the items exist.

## 1. Calibration target

| property | target | measured on the dev set |
|---|---|---|
| items | 400 (4 tasks × 100) | 20 |
| reference model mean (a mid open model, `doctrine`) | **0.45 – 0.65** | 0.878 |
| items at 1.00 across all calibration runs | **≤ 5%** | 35% |
| items at 0.00 across all calibration runs | ≤ 5%, and each one inspected for a rubric bug | 0% |
| per-task spread (max task − min task) | ≥ 0.15, so tasks are separable | 0.21 |
| items whose only checks are negative (`none_of`/`not_contains`) | **0** | 3 |

A set where a small model scores 0.88 cannot detect a 10-point improvement, which is exactly what H1 claims. The target band puts the reference model mid-range, where a real effect can move the needle.

## 2. Item blueprint — what varies inside each task

Each task gets 100 items from a **failure-mode × surface** grid, not from 100 rewordings of the same prompt. Every cell states which doctrine rule the item is testing.

### insight (100)

| failure mode | surface variants | n |
|---|---|---|
| names a vague audience ("年轻人") instead of a segment | 餐饮 / 教育 / 医疗 / 制造业 self-narrations | 25 |
| reports a feeling as a fact | monthly numbers that contradict the stated emotion | 20 |
| gives advice when the task asked for diagnosis | prompts that explicitly forbid advice | 20 |
| misses the relationship conflict | family / employer / co-founder / client | 20 |
| collapses two conflicts into one | narrations carrying two incompatible pulls | 15 |

### topic (100)

| failure mode | surface variants | n |
|---|---|---|
| audience drifts to "everyone" | niche verticals with small populations | 25 |
| no payable deliverable | topics that must map to a priced service | 25 |
| saturated angle offered as fresh | already-crowded subject areas (AI tools, side income) | 20 |
| topic is a keyword, not a promise | one-word subject prompts | 20 |
| contrarian framing without a condition | "argue the opposite" prompts that must state a condition | 10 |

### writer (100)

| failure mode | surface variants | n |
|---|---|---|
| opens with a platitude (`你是否也`, `在这个时代`) | long-form / short-form / listicle openings | 25 |
| promises an outcome (income, traffic, effectiveness) | ad copy, course pitch, product page | 25 |
| adjective pile-up instead of facts | spec sheets, feature lists | 20 |
| no concrete next action | endings, CTAs | 20 |
| violates a stated length budget | explicit budgets at 60 / 120 / 300 units | 10 |

### guard (100)

| failure mode | surface variants | n |
|---|---|---|
| merges platform-machine risk with substantive risk | drafts with both | 25 |
| quotes no position | drafts with several possible offenders | 20 |
| recommends deletion instead of a minimal fix | drafts worth saving | 20 |
| softens an unsupported claim into a wording note | claims with missing evidence | 20 |
| misses attribution/plagiarism | someone else's paragraph pasted in | 15 |

## 3. Anti-saturation rules (each item must satisfy all five)

1. **At least two independent failure modes.** An item with a single check is an item a model passes by luck.
2. **At least one positive requirement** (`contains`/`regex`/`min_units`), not only bans. Bans are free points for a silent or brief answer — that bug already cost us once.
3. **A distractor that satisfies the rule mechanically but not the doctrine.** Example: an item where writing "人群：25-35 岁女性" satisfies the label check but the doctrine also requires the segment be reachable by the product.
4. **A stated budget wherever a length check exists.** The rubric may not punish what the prompt did not ask for (amend 2 in `results/README.md`).
5. **A written "why this can fail" note** per item, one line, kept next to the item in an `<id>.why` field. If the author cannot name the failure, the item is a copy of an existing one.

## 4. Curation loop (uses the tooling that exists)

```bash
# 1. author 40 candidate items per task
# 2. run two reference models in both prompt modes (API, ~$1 per sweep)
python3 harness/cli.py --model remote --base-url ... --model-name A --prompt-mode raw \
  --out results/calib-A-raw.json
# 3. audit per item
python3 scripts/itemcheck.py --results results --out data/ITEM-AUDIT.md --flag any
# 4. repair or retire anything saturated / broken / unstable, repeat
```

Rules for the loop:

- An item at **1.00 across ≥ 3 runs and 2 models** is retired, not reworded — rewording a saturated item usually just moves the saturation.
- An item at **0.00 across ≥ 3 runs** is inspected for a rubric bug first. If the rubric is sound, the item is kept and labelled `hard`; hard items are legitimate, broken rubrics are not.
- An item with **spread ≥ 0.45** gets 5 runs before a verdict; on 2 observations it is noise, which is why `itemcheck.py` calls those `thin` rather than `usable`.
- Every retired item is recorded in this file with its final audit numbers, so the set's history is auditable.

## 5. Annotation

| step | rule |
|---|---|
| authors | 2 independent authors per task, neither aware of the SFT rows |
| overlap | 20% of items authored by both, reported as author-pair disagreement |
| adjudication | a third pass resolves disagreements; resolved items get a `note` field |
| agreement target | Cohen's κ ≥ 0.70 on the pass/fail decision per check; below that the check description is rewritten first |
| label style | the check label names the doctrine rule (`无效果承诺`), not the mechanic (`none_of(保证)`) |

Single-annotator authoring is the current state and a stated limitation in [`CARD.md`](CARD.md). Two-author overlap is what turns that into a measured limitation.

## 6. Held-out set (100 items)

Authored **after** the SFT corpus and the 400-item set are frozen, by someone who has not read the SFT rows. Used once. If an item is inspected before its single use, it is no longer held out — record any inspection in this file.

## 7. Effort and cost

| work | effort | cost |
|---|---|---|
| authoring 400 items + why-notes | ~65–80 h of focused work (10–12 min/item) | labour, no GPU |
| calibration sweeps (2 models × 2 modes × 3 rounds, API) | ~1 h of wall clock | **< $10** |
| audit and repair rounds | ~10 h | none |
| held-out 100 items | ~20 h | none |
| **total before touching a GPU** | **~2 working weeks** | **< $10** |

This is why the expansion is not on the GPU bill: it is a data-collection and review cost, and the GPU-hours are worthless until it is done. See [`../gpu-hours.md`](../gpu-hours.md) for the compute side, which assumes 400 items as input.

## 8. Definition of done

- [ ] 400 items, 100 per task, every item carrying a `why` note
- [ ] `scripts/itemcheck.py --flag saturated` exits 0 on the calibration reports
- [ ] reference-model mean inside 0.45–0.65 with per-task spread ≥ 0.15
- [ ] ≤ 5% saturated, ≤ 5% all-zero, and every all-zero item either repaired or labelled `hard`
- [ ] κ ≥ 0.70 on the 20% overlap
- [ ] held-out 100 authored and untouched
- [ ] dev set retired with its audit numbers recorded here
- [ ] `results/README.md` amend entry recording the switch from the dev set to the 400-item set
